# 注释规范

> 这个仓库的注释密度很高（`lib/src` 有 4888 条 `///`、2461 条行内 `//`，约 15% 的行是注释）。
> 这不是巧合，是刻意维持的资产 —— 但只有**写对位置**的注释才是资产。

## 判断标准：删掉这段注释，后来人会做错什么？

不会做错 → 不写。会做错 → 写。

| 该写 | 不该写 |
| --- | --- |
| 为什么是这个值（设计稿实测、规避了哪个回归） | 这个类叫什么、干什么（类名已经说了） |
| 为什么不用更直接的写法（试过什么、为什么不行） | 逐行翻译代码在做什么 |
| 这个约束改了会连带什么失效 | 给显而易见的参数加 `/// 标题` `/// 副标题` |
| 历史坑：曾经是 X，因为 Y 改成 Z，改回去会复现 | 任务流水账（「本次修改了…」「已修复…」） |

一句话版本：**注释解释代码无法解释的东西**。代码能说明 what，注释只补充 why 和 why-not。

## 三种注释，三种消化速度

```dart
/// 模块级：这个文件为什么存在、收什么不收什么。
///
/// 读者是第一次打开这个文件的人。用几段话说清边界，
/// 尤其是「这里故意不做什么」—— 那是后来人最容易想「补上」的地方。
abstract final class AppRadius { ... }
```

```dart
/// 成员级：为什么是这个值，一句话能说完就一句话。
///
/// 设计稿封面圆角 12，卡片本体/封面切口/选中描边共用，
/// 避免几处各写一个数后慢慢走样。
const videoCardRadius = 12.0;
```

```dart
// 行内：只在「代码看起来应该这么写，但这里必须那么写」时出现。
//
// 例：为什么这里关掉 InkWell 的 overlay、为什么用 clamp 而不是 min、
// 为什么这个判断要先于那个判断。
```

行内注释**不写**在赋值语句旁边解释变量名，也不写 `// 循环遍历列表`。

## 中文与标点

- 注释正文用简体中文，标识符、命令、日志保持原文。
- **中文注释句末加句号**：`/// 顶部背景图 + 渐变遮罩。`
  这一条有守卫（`test/comment_style_guard_test.dart`）盯着，
  只检查以中文标点结尾的完整句子，`/// - [Foo]`、`// ---- 分节 ----` 这类不算。
- 数字与中文之间不加空格（`16 高`），与图标/代码片段之间保留空格。
- 不用 emoji，不用「我们」（写「这里」「本仓库」）。

## 不该出现在注释里的东西

**过程性内容**。这类内容属于 issue、PR 描述或 commit message，不属于源码：

```dart
// ✗ 本次排查发现原来写的是 8，改成 16。先试了 12 效果不好，最后定了 16。
// ✓ 设计稿实测 16。取 8 时选中态比未选中态矮一截，看起来像「一选中尺寸就变了」。
```

区别在于：前者记录**我做了什么**，后者记录**为什么必须是这个值**。
前者三个月后毫无价值，后者三个月后仍然阻止一次回归。

**时间戳式表述**：「2026-10 清理时删除」可以留在 `docs/` 的变更记录里，
不要让它成为读代码时唯一能解释「这里为什么空着」的线索。真要留，就写**约束本身**：
「玻璃材质退役后此处不再有材质档，卡片直接用 surface」。

## 什么时候删注释

注释和代码一起演进。出现下面任一情况，注释就要改或删：

- 代码已经改成注释描述的样子（注释在追述历史）
- 引用的文件/函数/令牌已不存在（失效的 `[Foo]` 链接）
- 注释和代码矛盾 —— **这时视为 bug**，优先级高于「注释和代码都不对」的情况，
  因为矛盾本身会把人带偏。

`test/comment_style_guard_test.dart` 只做机械可判的部分（当前是句号）。剩下的靠这条纪律：
**改了一个值，就顺手把它的注释读一遍。**

## 注释与测试的分工

能用测试固定的事实，不要只写在注释里。

- 「这个值不能小于 X」→ 注释说明原因 + 测试断言边界。
- 「这个守卫要能拦住 Y 写法」→ 测试里**故意构造一次违规**，证明守卫不是永远绿的。
- 「这里曾经因为 A 出了 bug」→ 注释写清 A 的复现条件，测试覆盖 A。

`test/surface_token_guard_test.dart` 是范本：它既拦真实代码，也喂正则一段违规片段，
还反向确认合法写法不会被误报。守卫测试最容易写坏的地方就是「永远为真」。
